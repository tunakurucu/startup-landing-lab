Open-source job queue for Node

Know where every background job is.

Drumbeat moves slow work out of the request. Each job carries its state (queued, active, retrying, completed or failed) along with its attempt count and the error that put it there.

Read the docs

The local example runs in memory. No server, account or API key.

The lifecycle

Five states, and only one at a time.

A job is always in exactly one state. Step one through it below: make the handler throw, watch the backoff double, and run out of attempts to see where a failed job ends up.

    Runs in this page only. Policy shown: 3 attempts, exponential backoff starting at 200ms.

    queued

    Stored and waiting for a worker. A retried job returns here when its backoff ends.

    active

    Claimed by one worker. Your handler is running and the attempt counter has been incremented.

    retrying

    The handler threw with attempts remaining. The error is kept and the next run time is set.

    completed

    The handler returned. Terminal. The return value is kept with the job.

    failed

    The last allowed attempt threw. Terminal. The job and its error stay put until you act on them.

    Try it locally

    One file. No Redis, no account, no API key.

    This example uses the in-memory store, so nothing leaves your machine and nothing persists after the process exits. The handler fails on purpose twice, then succeeds, so you can watch a retry happen.

    1. 1Make a scratch folder and install
      terminal
      mkdir drumbeat-demo && cd drumbeat-demo
npm init -y && npm install drumbeat
    2. 2Save this as retry-demo.mjs
      retry-demo.mjs
      // Runs entirely in memory. Nothing is sent anywhere.
import { Queue, MemoryStore } from 'drumbeat';

const queue = new Queue({ store: new MemoryStore() });

let calls = 0;
queue.define('flaky', async (job) => {
  calls += 1;
  // Simulate a transient error on the first two attempts.
  if (calls < 3) throw new Error(`simulated failure ${calls}`);
  return { ok: true, input: job.data };
}, { attempts: 3, backoff: { type: 'exponential', delay: 200 } });

for (const event of ['active', 'retrying', 'completed', 'failed']) {
  queue.on(event, (job) => {
    console.log(event.padEnd(10), `attempt ${job.attempt}/${job.maxAttempts}`,
      job.lastError?.message ?? '');
  });
}

await queue.start();
await queue.enqueue('flaky', { n: 1 });
await queue.drained();
await queue.stop();

    Before you adopt it

    What to plan for.

    A queue changes how failures show up in your system. These are the behaviours worth designing around on day one.

    Handlers can run more than once

    If a worker dies mid-attempt, the job is retried. Write handlers so a repeat is harmless: check before you charge, upsert instead of insert.

    The memory store is for development

    It makes the example above work with zero setup, and it loses every job on restart. Use a persistent store in production; the docs list which ones are supported.

    Retry policy lives with the job

    Attempts and backoff are set where you define a job, so a payment webhook and a thumbnail resize can fail differently.

    Failed jobs wait for you

    A failed job keeps its data and last error. Nothing re-runs it automatically. You inspect it, fix the cause, and re-enqueue.

    No throughput numbers on this page

    We haven't published benchmarks, so we won't quote jobs per second. Throughput depends on your store, payload size and handler. Measure on your own workload before you size workers.

    Where to start

    Start with one app. Read further before you run it for many.

    Adding jobs to your app

    Run the local example, then move one slow call (an email, an export, a webhook) behind enqueue. Keep the memory store until you deploy.
