# Drumbeat landing page: notes

## Direction

- **Primary reader: the developer who would add the dependency.** That is the person who reads docs and runs `npm install`. It covers solo developers and engineers on small teams. Platform teams get their own path in "Where to start", which tells them what to read before they run Drumbeat for other teams. I didn't write two parallel pitches. The brief leaves the audience open, and one page that tries to serve both usually serves neither.
- **The page explains the job lifecycle, because that's what the client asked for.** The hero is an illustrative job record (state log plus a beat track whose backoff gaps double). The second section is an in-page simulator: the reader makes the handler throw or return and watches the state, attempt count, next run time and last error change on a state diagram.
- **Credibility comes from candour, not proof points.** No logos, testimonials, stars, download counts or performance numbers appear anywhere. The "What to plan for" section covers at-least-once execution, a memory store that is for development only, and failed jobs that need manual action. It also says outright that no throughput benchmarks are published.
- **Visual identity:** warm paper and ink with one orange accent, plus five fixed state colours used the same way everywhere (tags, log, diagram). The wordmark is a run of beats. Fonts are system sans and system mono only. Dark mode follows `prefers-color-scheme`.

## Assumptions to verify before launch (important)

The brief gave no API or links, so all of these are placeholders:

1. **The API in the example is assumed.** `Queue`, `MemoryStore`, `queue.define(name, handler, { attempts, backoff })`, `queue.on(event, job => ...)`, `job.attempt`, `job.maxAttempts`, `job.lastError`, `queue.start()`, `queue.enqueue()`, `queue.drained()` and `queue.stop()` all need to be replaced with the real API. The "expected output" block must then be regenerated by actually running the file.
2. **The state names** (`queued`, `active`, `retrying`, `completed`, `failed`) and the model "retrying → queued when the backoff elapses" are assumed. Event names in the example match these states.
3. **An in-memory store exists** and needs no server. The brief's "works locally without a server" suggests this, but it isn't confirmed.
4. **Behaviour claims in "What to plan for":** at-least-once delivery, per-job retry policy, failed jobs kept until someone acts on them with no automatic re-run, and production stores documented in the docs. Change or remove any that don't match Drumbeat.
5. **The npm package name is `drumbeat`.** Check that this name is actually the client's package on npm.
6. **Links:** "Read the docs" points to `docs/` (relative). There's no GitHub link and no license is named, because I didn't want to invent a repo URL or license. Add both once known; the footer has room.
7. The backoff policy in the hero and simulator (3 attempts, exponential from 200ms) and the error strings are illustrative. Both are labelled that way on the page.

## Files

- `index.html`: page markup. All content is readable with JavaScript off.

- `favicon.svg`

## Testing done

Tested with Playwright (Chromium) against `file://` at 1366, 820, 390, 360 and 320px wide, in light and dark:
- no requests that aren't `file:`, no console errors, no horizontal overflow
- the simulator reaches `failed` after three throws and `completed` on a return
- the copy button shows confirmation
- keyboard focus stays on the action buttons after each step
- the page renders with JavaScript disabled

Not tested: Safari/Firefox rendering, screen-reader pass with a real AT.
