How a Drumbeat job moves

Drumbeat runs work that shouldn’t block a request (sending a receipt, calling a webhook, resizing an image) as a job. This guide follows one job from the moment you add it to the moment it is completed or failed, and shows how to read its state at every step.

Install

npm install drumbeat

Drumbeat is a Node package. Everything in this guide runs in one Node process with the memory store, so you need no Redis, server, account or API key to follow along.

Your first job

Create a queue, define a handler for a job name, then add a job with its data and a retry policy.

import { createQueue } from 'drumbeat';

const queue = createQueue({ store: 'memory' });

queue.define('send-receipt', async (job) => {
  // call your mail provider here; return whatever should be stored as the result
  return { sentTo: job.data.to };
});

await queue.add('send-receipt', { to: 'ada@shop.example' }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 1000 },
});

add() returns as soon as the job is saved as queued. Call it from a request handler and the response does not wait for the work.

States

A job is in exactly one state at a time. Retries reuse the same job: its ID, data and history carry through every attempt.

StateMeaningLeaves when
queuedSaved, waiting for a worker.A worker picks it up → active.
activeThe handler is running one attempt.Returns → completed. Throws with attempts left → retrying. Throws on the last attempt → failed.
retryingWaiting out the backoff delay after an attempt threw. The error is recorded.The delay passes → active.
completedThe handler returned; its value is the job’s result.Final.
failedThe last allowed attempt threw. The final error is kept.Final, unless you retry it by hand.

Retry policy

attempts counts the first run, so attempts: 3 means one run and up to two retries. backoff sets the wait before each retry:

  • { type: 'fixed', delay } waits delay milliseconds every time.
  • { type: 'exponential', delay } waits delay × 2^(n−1) before attempt n+1: with delay: 1000, that is 1 s, 2 s, 4 s and so on.

The wait comes on top of your handler’s own run time. To see the full schedule for a policy before you ship it, use the retry planner.

Events

Every state change emits job:state. Forward it to the logs or metrics your team already watches.

queue.on('job:state', (e) => {
  // e.id, e.name, e.state, e.attempt, e.error, e.elapsed
  logger.info({ job: e.id, name: e.name, state: e.state, attempt: e.attempt, err: e.error?.message });
});

Because a retried job keeps its ID, filtering your logs by job shows every attempt of one job in order.

The memory store

store: 'memory' keeps jobs inside the Node process. It is meant for local runs and tests: when the process exits, every job in it is gone, including jobs waiting to retry. Don’t put production traffic on it.

Writing handlers

  • Make them safe to run twice. An attempt can do its work and still throw (a timeout after the email went out). Use job.id as the idempotency key you send to providers.
  • Throw to retry, return to finish. A thrown error schedules the next attempt if one is left; a returned value completes the job.
  • Set a ceiling. A failed job with its last error is something you can alert on; endless retries hide the fault.
