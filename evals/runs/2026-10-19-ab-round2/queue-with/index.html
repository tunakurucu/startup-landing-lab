drumbeat · open-source job queue for Node.js

Follow every job from enqueue to its last retry.

Move work that shouldn’t block a request (receipts, webhooks, image resizes) into Drumbeat. Each job keeps one ID and one history across every attempt, so you can always say whether it is queued, running, waiting to retry, completed or failed, and why.

Run it on your laptop first

One file, one Node process. The memory store needs no Redis, no server, no account and no API key, and nothing leaves your machine. The script fails its first attempt on purpose so you can watch a retry happen.

  1. Install the package in any folder with a package.json.

    $npm install drumbeat

  2. Save the script as retry-demo.mjs.

  3. Run node retry-demo.mjs. Each line is one state change of the same job.

retry-demo.mjs

Illustrative API: confirm names in the docs

// One Node process. No Redis, no server, no account, no API key.
import { createQueue } from 'drumbeat';

const queue = createQueue({ store: 'memory' });

let calls = 0;
queue.define('send-receipt', async (job) => {
  calls += 1;
  // Nothing is sent: a real handler would call your mail provider here.
  if (calls === 1) throw new Error('SMTP timeout (simulated)');
  return { sentTo: job.data.to };
});

queue.on('job:state', (e) => {
  console.log(e.elapsed, e.id, e.state, e.detail ?? '');
});

await queue.add('send-receipt', { to: 'ada@shop.example' }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 500 },
});

await queue.drain(); // resolves when nothing is queued, active or retrying

$ node retry-demo.mjs

Five states, and what moves a job between them

A job is always in exactly one of these. Retries never create a new job, so its ID, data and history carry through.

queued
Saved and waiting for a worker. Your request has already moved on.
in: add()
out: worker picks it up → active
active
Your handler is running one attempt. The attempt number is on the job.
out: handler returns → completed
out: throws, attempts left → retrying
out: throws, none left → failed
retrying
The last attempt threw and more are allowed. The job waits out its backoff delay with the error recorded.
out: delay passes → active, same ID
completed
The handler returned. Its return value is the job’s result; earlier errors stay in the history.
final
failed
The last allowed attempt threw. Nothing else is scheduled; the job keeps its final error so you can alert on it or retry it by hand.
final

Before you depend on it

What a team running Drumbeat behind real traffic needs to plan around.

Make handlers safe to run twice

A retry calls the same handler with the same job ID and data. If attempt 1 sent the email and then timed out, attempt 2 sends it again unless you check. Pass the job ID to your mail or payment provider as the idempotency key.

The memory store lives inside your process

It is for local runs and tests. When the process exits, every job in it is gone, including ones waiting to retry, so don’t put production traffic on it.

Give every job a last attempt

A job that retries forever hides the fault. A failed job with its final error is something you can alert on and replay. Size the ceiling with the retry planner above.

Send state changes where your team already looks

Every transition is an event carrying the job ID, name, state, attempt and error, so you can count failures per job name or follow one job across attempts in the logs you already have.

queue.on('job:state', (e) => logger.info({
  job: e.id, name: e.name, state: e.state,
  attempt: e.attempt, err: e.error?.message,
}));
