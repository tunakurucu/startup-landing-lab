Catch schema drift in CI, not in a failed deploy.

Driftcheck builds the schema your migrations would produce, reads the schema actually running in production, and fails the job if the two disagree. Postgres and MySQL. One command.

$ npx driftcheck

This is what the job prints when someone has hand-patched a column in production. The deploy stops here, on a pull request, instead of at six in the evening.

What drift is

Your migrations describe a schema. Production runs one. They start out the same and quietly diverge: a hotfix applied by hand, an index dropped during an incident, a migration edited after it already ran.

Driftcheck applies your migrations to a scratch database and diffs the result against the target, object by object.

  • ~differs between the two
  • +exists only on the target
  • -exists only in migrations

Where it runs

Add one step to the pipeline that already runs on every pull request. Point it at a read-only replica or a recent snapshot; Driftcheck only reads the target schema and never writes to it.

The exit code is the whole integration. Anything that can run a shell command can gate a deploy on it.

# .github/workflows/schema-check.yml
name: schema-check
on: [pull_request]

jobs:
  driftcheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx driftcheck --migrations ./db/migrations --target "$DATABASE_URL"
        env:
          DATABASE_URL: ${{ secrets.REPLICA_READONLY_URL }}
exit 0
No drift. The schemas match and the deploy can proceed.
exit 1
Drift found. The job fails and the report lists every differing object.
exit 2
Driftcheck itself could not run: bad connection string, unreadable migrations, unsupported database.

What it compares

Every object the migrations create is checked against the target by name, then by definition. Ordering of columns and whitespace in defaults are ignored; types, nullability, and constraints are not.

ObjectWhat is compared
TablesPresence, schema, and ownership of every table the migrations create.
ColumnsType, length and precision, nullability, default expression, identity and generated columns.
IndexesColumns, order, uniqueness, method, partial predicates, and included columns.
ConstraintsPrimary keys, foreign keys with their on-delete and on-update actions, unique and check constraints.
Enums and typesPostgres enum values in order; MySQL ENUM and SET column definitions.
Sequences and viewsSequences the migrations own, and view definitions after normalisation.

What this is, plainly

  • Free and MIT licensed. Use it, fork it, vendor it. There is no paid plan and no company behind it.
  • A single command. npx driftcheck downloads nothing beyond the package and needs no agent, account, or dashboard.
  • Read-only against the target. It introspects the schema. It does not run your migrations in production and does not fix drift for you.
  • Postgres and MySQL. Other databases are not supported yet. If you need one, open an issue and say which.

Run it once against production. If it finds nothing, you have lost two minutes.

$ npx driftcheck
