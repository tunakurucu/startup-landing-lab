Fail the CI job, not the 6 pm deploy.

Driftcheck is an open-source CLI for backend and platform engineers. It compares the schema your migrations will produce with the one production is running, and fails CI before a deploy that would break.

npx driftcheck

Free and MIT licensed, for Postgres and MySQL. Every line that reads your database is on GitHub.

Sample database and example output, written for this page. It runs in your browser and connects to nothing.

Change production by hand, then run the check

What someone ran in production:

✕driftcheck failed · deploy blockedexit 1
-- run by hand in production:
CREATE INDEX orders_created_at_idx ON orders (created_at);

$ npx driftcheck
✕ orders: index orders_created_at_idx is in production, not in migrations/
1 difference · exit code 1

Why it would break: a later migration that creates orders_created_at_idx fails, because the name is already taken.

Understands ADD, DROP, ALTER TYPE and RENAME COLUMN, and CREATE or DROP INDEX.

It reads two schemas and fails the job when they differ

One side is the schema your migration files will produce. The other is the schema production is running right now. Driftcheck compares them and sets the exit code, so your CI decides whether the deploy starts.

migrations/

The files in your repo, including the ones this branch adds.

will produce

The schema those files add up to.

production

The database your deploy will run against.

is running

The schema it has today, hand-run fixes included.

npx driftcheck

Compares the two and reports each difference.

exit 0They match. The deploy step runs.

exit ≠ 0They differ. The job fails before deploy.

Add one step in front of your deploy step

Run npx driftcheck in the same job, before the deploy. Any CI that stops on a failing command will stop there, and the deploy never starts.

It needs to reach your production database to read its schema. The docs cover how to connect it for Postgres and MySQL.

Example config. The order of the steps is the point; connection settings are in the docs.

# .github/workflows/deploy.yml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check schema drift
        run: npx driftcheck
      - name: Deploy
        run: ./scripts/deploy.sh
# .gitlab-ci.yml
stages: [check, deploy]

driftcheck:
  stage: check
  image: node:20
  script:
    - npx driftcheck

deploy:
  stage: deploy
  script:
    - ./scripts/deploy.sh
# any CI runner with Node and a shell
# the deploy only runs if driftcheck exits 0
npx driftcheck && ./scripts/deploy.sh

It replaces the check script someone wrote once

Most teams find drift one of two ways today: a deploy fails, or a hand-written script catches what its author thought to check. Here is the change, in the format you already read every day.

  1. your-release-process.md
  2. −Before: find out when the 6 pm deploy fails on a migration
  3. −Before: keep a check_schema.sh that one person wrote and nobody updates
  4. +After: find out when the CI job fails, before the deploy starts
  5. +After: run npx driftcheck, an MIT-licensed CLI whose code you can read
