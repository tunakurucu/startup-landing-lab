The test that only fails in CI, failing on your laptop.

Rerun records a failing test run in CI and replays it exactly where you can put a breakpoint in it. Same inputs, same timing, same network responses. Free, MIT-licensed, one command to install.

$ npm install -g @rerun/cli

Three commands, start to breakpoint

Rerun wraps your existing test command. It doesn’t replace your runner, your assertions, or your CI provider.

  1. Record in CI

    Put rerun record in front of the test step. On a green run it adds a few hundred milliseconds and writes nothing. On a red run it saves a recording as a build artifact.

    # .github/workflows/test.yml
- run: npx @rerun/cli record -- npm test

  2. Get the recording id from the failed job

    The failure summary in the CI log ends with one line. Copy it.

    1 failing · recording saved · rerun replay ci-8f3a2c

  3. Replay it locally

    Rerun fetches the recording, restores the environment, pins every network response, and runs the same command. Add --inspect to attach your debugger before the first line runs.

    rerun replay ci-8f3a2c --inspect

What a recording contains

A recording is a single file. It holds everything the test process observed that could differ between CI and your machine, and nothing that is the same on both.

A typical recording for one failing Jest file is 1–5 MB. Recordings are build artifacts; they live wherever your CI already keeps artifacts and expire on the same schedule.

Source of differenceWhat Rerun does on replay
EnvironmentRestores argv, environment variables, working directory, locale, timezone, and the Node version (via your version manager if installed).
TimeReplays Date.now, performance.now, and timer order so that a 2,003 ms timeout fires at 2,003 ms, not whenever your laptop gets to it.
RandomnessReplays Math.random, crypto.randomUUID, and crypto.randomBytes with the recorded values.
NetworkServes every HTTP and HTTPS response the test received, in the order and at the latency it received them. Your laptop never contacts the real service.
DNS and portsResolves the hostnames the test resolved and reserves the ports it got.
Filesystem readsSnapshots files the test read outside the repository checkout, such as temp files and caches.
SchedulingReplays the order in which concurrent promises and I/O callbacks resolved, which is where most “only in CI” failures come from.
Not yetChild processes, WebSockets, and native addons. Rerun warns at record time if the test touches any of these, so you know before you replay.

Secrets in environment variables and response bodies are redacted at record time with the same rules your CI provider uses for log masking. You can add your own patterns.

Questions engineers ask first

Does my code or test data leave my CI?

No. Rerun has no server. Recordings are written to disk in the CI job and stored with your other build artifacts. rerun replay fetches them with the same credentials you already use for your CI provider.

What happens if the test passes on replay?

Rerun tells you, and prints a diff of what the process observed versus what was recorded. In practice that means the failure depends on something in the “not yet” row above. That is useful information on its own, and it is the first thing we would like to hear about.

Why not just retry the test?

Retrying hides the failure until it reaches production. Replaying it lets you step through the actual interleaving that broke, fix the race, and delete the retry.

How much does recording slow down CI?

A few hundred milliseconds of startup, and roughly 2–4% on the test run itself, in our measurements on Jest suites between 500 and 5,000 tests. Numbers and the benchmark script are in the repository.

Does it work for languages other than JavaScript?

Not today. The recorder hooks into Node’s module loader and async_hooks, which is why it can capture scheduling without changing your code. Other runtimes would need their own recorder; the replay format is runtime-neutral and we would welcome one.

Can I try it without touching my CI config?

Yes. rerun record -- npm test works on your laptop too, so you can record a local run and replay it to see what the tool captures. The repository also includes the recording from the session above, examples/ci-8f3a2c, which you can replay as-is.
